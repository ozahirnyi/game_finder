# Playfinder unified Lightsail site design

## Goal

Publish the complete application from Lightsail at `https://example.com` and
remove Railway from active source, deployment configuration, and user-facing
documentation. Visitors use one public origin; the API is available only under
the same origin's `/api/` prefix.

## Architecture

Nginx terminates TLS for `example.com` and has two routes:

1. `/api/` proxies to the FastAPI container at `127.0.0.1:8000`, strips the
   `/api` prefix, and forwards the original host and HTTPS scheme.
2. Every other path proxies to the Next.js `web` container at
   `127.0.0.1:3000`.

The frontend is built with `NEXT_PUBLIC_API_URL=/api`, so all browser requests
stay on `example.com`. This avoids route conflicts between Next.js pages and
the existing unprefixed FastAPI routes while keeping a single public domain.

Docker Compose runs the existing API, Postgres, Redis, and a production Next.js
web service. Nginx is kept on the host as it is today. The deployment workflow
updates the Lightsail checkout and Compose services from `main`.

## Configuration and authentication

Production settings use only the domain values below:

- `FRONTEND_ORIGIN`, `FRONTEND_ORIGINS`, `FRONTEND_PUBLIC_URL`:
  `https://example.com`
- `BACKEND_PUBLIC_URL`: `https://example.com/api`
- `GOOGLE_REDIRECT_URI`:
  `https://example.com/api/auth/google/callback`

OAuth and Steam callbacks retain their existing FastAPI handlers; the
`/api` proxy prefix makes their public callback URLs unambiguous. Google Cloud
Console must be updated with the new redirect URI after deployment.

## Railway removal

Remove Railway URLs, Railway-specific environment fallbacks, Railway host
allow-lists, and Railway deployment guidance from active application code,
environment examples, compose files, and README instructions. Existing dated
design and plan documents are historical records and are not runtime or
deployment configuration; they remain unchanged.

## Validation

Automated tests cover the Nginx proxy split and public URL configuration.
Before release, run the backend suite and frontend production build. After
deployment, verify the home page, a same-origin `/api/health` request, HTTP to
HTTPS redirect, and a Google callback URL generated by the API.
